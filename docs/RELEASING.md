# Выпуск версий

## Как устроена сборка

Workflow `.github/workflows/build.yml` запускается при каждом push в `main` (и вручную
кнопкой **Run workflow**):

1. модульные тесты обеих сборок;
2. релизная сборка `assembleRelease` — обычная (`standard`) и с Tor (`tor`);
3. публикация APK и `SHA256SUMS.txt` в GitHub Releases.

Сборки отличаются только встроенным Tor; идентификатор приложения, версия и подпись у них
общие, поэтому одна ставится поверх другой.

Тег и тип релиза определяются по `versionName` в `app/build.gradle.kts`:

| versionName | Тег | Тип |
|---|---|---|
| `1.1.0` (без суффикса) | `v1.1.0` | обычный релиз |
| `1.2.0-rc1` (с суффиксом) | `v1.2.0-rc1-build.N` | pre-release на каждый push |

Если релиз с таким тегом уже есть, новый не создаётся — нужно поднять версию.

## Выпуск новой версии

1. В `app/build.gradle.kts` увеличьте `versionCode` (на 1) и задайте `versionName`.
2. Добавьте описание изменений:
   - `CHANGELOG.md`;
   - `fastlane/metadata/android/ru-RU/changelogs/<versionCode>.txt` и `en-US/…`
     (до 500 символов; используется как текст релиза).
3. Влейте в `main`. Через несколько минут релиз появится в Releases. Установленные
   приложения узнают о нём сами в течение суток (`UpdateChecker`): сравнивают тег
   последнего выпуска со своей версией и предлагают скачать приложенный к нему APK.

К обычному выпуску прикладываются четыре APK:

| Файл | Что это |
|---|---|
| `DP_Call-v<версия>.apk` | обычная сборка |
| `DP_Call.apk` | она же с постоянным именем |
| `DP_Call-Tor-v<версия>.apk` | сборка с Tor |
| `DP_Call-Tor.apk` | она же с постоянным именем |

Постоянные имена нужны для ссылок
`https://github.com/dpsmpx/DP_Call/releases/latest/download/DP_Call.apk` (её рассылает
кнопка «Пригласить») и `…/DP_Call-Tor.apk`. Не переименовывайте файлы: проверка
обновлений в приложении выбирает APK своей сборки по началу имени (`DP_Call-v`,
`DP_Call-Tor-v`). Постоянные копии к pre-release не прикладываются, чтобы ссылки не вели на
непроверенную сборку.

Чтобы обновление установилось поверх старой версии, выпуск должен быть подписан тем же
ключом и иметь больший `versionCode`. Pre-release приложение не предлагает.

Между выпусками удобно держать в `main` версию с суффиксом (`1.2.0-dev`), чтобы каждая
сборка публиковалась как pre-release.

Изменения только в документации (`*.md`, `docs/`, `fastlane/`) сборку не запускают.

## Подпись

Выпуски подписываются ключом из секретов репозитория (`DPCALL_KEYSTORE_*`). Без них
обычный релиз не собирается — сборка завершается ошибкой.

Промежуточные сборки (версия с суффиксом) при отсутствии секретов подписываются общим
тестовым ключом `app/debug.keystore` из репозитория. **Этот ключ публичный**: кто угодно
может собрать APK с той же подписью, поэтому для распространения он не годится.

Файл ключа и пароли храните в надёжном месте с резервной копией: без них нельзя выпускать
обновления, а смена ключа потребует от всех пользователей переустановки (и их коды сменятся).

### Свой ключ подписи

Если ключ уже есть (файл `.jks` или `.p12`), шаг 1 пропустите. Хранилище PKCS#12 (`.p12`)
подходит без преобразований; пароль ключа у него совпадает с паролем хранилища.
Имя ключа (alias) можно узнать так:

```bash
keytool -list -v -keystore dppass-dev.p12 -storetype PKCS12 | grep -E "Alias|SHA256"
```

1. Создайте хранилище (один раз; сохраните файл и пароли в надёжном месте — без них
   обновления выпускать будет нельзя):

   ```bash
   keytool -genkeypair -v -keystore dpcall-release.jks -alias dpcall \
     -keyalg RSA -keysize 4096 -validity 10000
   ```

2. Закодируйте его в base64:

   ```bash
   base64 -w0 dpcall-release.jks > dpcall-release.jks.b64
   ```

3. В GitHub: **Settings → Secrets and variables → Actions → New repository secret**:

   | Секрет | Значение |
   |---|---|
   | `DPCALL_KEYSTORE_BASE64` | содержимое `dpcall-release.jks.b64` |
   | `DPCALL_KEYSTORE_PASSWORD` | пароль хранилища |
   | `DPCALL_KEY_ALIAS` | `dpcall` |
   | `DPCALL_KEY_PASSWORD` | пароль ключа |

4. Поднимите версию и влейте в `main` — релиз будет подписан вашим ключом.

Смена ключа подписи означает, что установленное приложение нельзя обновить поверх: его
придётся удалить, и код пользователя сменится. Поэтому ключ лучше подключить до того, как
приложением начнут пользоваться.

## Проверка релеев

Список публичных релеев — `RelayPool.DEFAULT_RELAYS`, запасные — `RelayPool.SPARE_RELAYS`. Перед выпуском стоит убедиться, что
они по-прежнему доставляют вызовы:

```bash
DPCALL_LIVE_RELAYS=1 ./gradlew testStandardDebugUnitTest --tests '*Live*' -i | grep LIVE
```

## Минификация

Релизная сборка минифицируется R8 (`isMinifyEnabled`, `isShrinkResources`) и содержит
нативные библиотеки только для ARM (`arm64-v8a`, `armeabi-v7a`) — APK около 22 МБ вместо 61.
Отладочная сборка не минифицируется и включает x86 для эмуляторов.

Правила сохранения — `app/proguard-rules.pro`: классы WebRTC и secp256k1 (вызываются из
нативного кода), обработчик звука, сериализаторы моделей. После изменения зависимостей или
правил проверьте на телефоне звонок целиком именно на релизной сборке: ошибки R8
проявляются только при запуске.

Файл `mapping.txt` для расшифровки стек-трейсов сохраняется в артефактах сборки GitHub Actions.

## Кандидаты в релиз

Версию, которую нужно сначала проверить на устройствах, выпускайте с суффиксом
(`1.0.1-rc1`): она публикуется как pre-release, и приложение не предлагает её как обновление. После проверки
уберите суффикс и влейте в `main` — выйдет обычный релиз с тем же `versionCode`.

## Tor

Сборка `tor` берёт из `info.guardianproject:tor-android` только нативную `libtor.so`
(задача `extractTorNative`), а Java-обёртку `org.torproject.jni.TorService` — исходником из
sources jar той же версии (`app/src/tor/java/org/torproject/jni/`, лицензия BSD-3 в
`app/src/tor/TOR-ANDROID-LICENSE`). Классы из AAR не подходят: начиная с 0.4.9.11 они
собраны под Java 24 и compileSdk 37, которые наш набор инструментов не принимает.

Мосты: `com.netzarchitekten:IPtProxy` (Lyrebird и Snowflake, Go). Встроенные мосты —
`app/src/tor/assets/builtin_bridges.txt`, из `projects/tor-expert-bundle/pt_config.json`
репозитория tor-browser-build; при выпуске стоит обновлять их из свежего Tor Browser.
Сборка tor хранит нативные библиотеки сжатыми (`useLegacyPackaging`), иначе APK был бы
около 85 МБ.

Обновление Tor: поменяйте `TOR_ANDROID_VERSION` в `app/build.gradle.kts`, замените
`TorService.java` файлом из `tor-android-<версия>-sources.jar` (Maven Central) и версию в
`org/torproject/jni/BuildConfig.java`. Затем соберите `assembleTorRelease` и проверьте на
телефоне, что плашка доходит до «На связи через Tor».

## Experimental APK (1.3.1+)

Workflow дополнительно собирает `DP_Call-Experimental-v<версия>.apk` из flavor
`experimental`. У него applicationId `com.dpsmpx.dpcall.experimental`, отдельные
ключи и контакты; он не заменяет стандартный или Tor APK. Имя постоянного файла
не публикуется, автоматическое обновление этой сборки отключено.

Перед Gradle workflow запускает `carrier/build.sh`: закреплённые MIT-исходники,
Go race tests, gomobile AAR для ARM и ARM64. Затем тесты и lint всех трёх вариантов
и `assembleRelease`. PR собирается с публичным тестовым ключом; после слияния в
main — с ключом из Secrets и публикацией релиза. PR не публикует релиз.
[Требования и архитектура адаптера](../carrier/UPSTREAM.md).
